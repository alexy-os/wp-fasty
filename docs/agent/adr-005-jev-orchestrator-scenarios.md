# ADR-005 — 12 будущих сценариев Jev для агента-оркестратора

Дата: 2026-11-07 (Europe/Moscow, UTC+3).
Статус: **будущие сценарии / proposed**, документирование одобрено t212; реализации и live-вызовов нет.
Продолжает [ADR-002](adr-002-builder-agent-governance.md) и [этап 1 roadmap](builder-agent-roadmap.md#1-optional-jev-advisor-and-local-evidence-dataset--future).
Не меняет завершённое [наследование темы](adr-004-theme-appearance-inheritance.md).

## Источник и граница достоверности

Все 12 названий и цитаты ниже извлечены из owner Page
[«12 агентных сценариев Jev»](https://12-agentnykh-stsenariev-jev-nlrf.pages.grok.bot/).
Источник фактически прочитан через приватную Library владельца; внешний URL не является обещанием
публичной доступности. Приватный canonical/store URL здесь не публикуется.
Цитата передаёт идею исходной Page; абзац «Предлагаемая адаптация» — наш будущий дизайн, не описание реализации.
Упоминания CodeGen-X, ContentlY, chaosbun, Jevgrep и Beacon в Page не доказывают наличие таких интеграций в Builder.

[Официальный System One API](https://docs.typesafe.ai/api/system-one.md) прочитан в этой задаче:
`POST /v1/systemone` принимает model/state/именованные questions и возвращает typed answers, фактическую model и usage.
Для этого плана рассматриваются `noul` (вероятность yes), `choice` (закрытые варианты) и `score` (упорядоченная рубрика;
ответ — ожидаемая оценка, возможна дробь). Несколько типов вопросов допустимы в одном запросе.
API также описывает gated image/box-вопросы; их включение здесь не планируется.
API не реализует за нас browser tools, compaction, поиск кода, память, merge или CI-оркестрацию.

Стабильность, экономия, скорость и качество сценариев — гипотезы для нашей оценки, не гарантии API.
Числа цены/задержки и сравнений из Page не принимаются за измерения Builder, SLA или бюджет.
Вероятность/confidence не равны доказанной корректности; правила допуска и пороги надо калибровать по экспертным labels.

## Общая власть оркестратора и безопасность

- Jev — типизированный **советник, не финальный решатель**. Главный агент может отвергнуть рекомендацию,
  уточнить критерии, повторно запросить shortlist или задать вопрос человеку. Слова «выбирает/решает» в цитатах
  не передают модели право выполнять действия. Нет свободного объяснения от Jev или автоматически вызванных tools.
- Неизменяемые Platform/capabilities/schema/revisions/sandbox/CSP, разрешения на публикацию и человеческое
  подтверждение внешних действий всегда сильнее модельной оценки. Advice не расширяет tool allowlist.
- Local-first остаётся рабочим без Jev. Нет нового MCP/HTTP search/updater, сетевой зависимости или Jev-кода
  в текущем локальном поиске. Ошибка/timeout/auth/schema mismatch — не «пустая выдача» и не уверенное no-fit.
- Будущий remote adapter — только после отдельного согласия: минимизация/редакция state, права на источники,
  лимиты токенов/запросов/времени, cancellation, контролируемые retries/cache и локальный fallback.
  Ключи остаются в local-wp vault, не в prompts/WP options/датасете. Не отправлять credentials, приватные формы
  или полные traces по умолчанию. Late reply не заменяет уже принятое решение.
- Проверять ответ, ID кандидатов и версии. Записывать provenance вопроса/рубрики, policy/skills/catalog/model,
  реальный usage и решение главного агента (accept/disagree/requery), а не скрыто превращать advice в истину.
  Сбор/экспорт evidence — отдельное добровольное согласие, retention и удаление по ADR-002; не default telemetry.

## Двенадцать сценариев — исходные формулировки и будущая адаптация

### 1. Следующее действие в браузере

> Страница сначала превращается в структурированный текст; Jev выбирает только из допустимых пар «операция–цель».

Предлагаемая адаптация: Будущий отдельный browser adapter передаёт очищенное структурированное DOM state и закрытые ID пар операция–цель (CLICK/TYPE/STOP); `choice` советует шаг. Оркестратор проверяет свежесть DOM, существование цели и разрешённое действие; STOP/уточнение при сомнении. Это не существующий инструмент Builder, не право на shell, сеть, ввод секретов или самостоятельную отправку форм.

### 2. Сжатие контекста

> Выбирает, какие события выживают; не пересказывает и не придумывает замещающий текст.

Предлагаемая адаптация: Для локальной трассы предлагаются `noul`/`score` по ID событий; код собирает дословное подмножество с ссылками на оригинал, не сгенерированный пересказ. Обязательные ограничения, решения пользователя и незавершённые действия нельзя отбрасывать по одному совету; проверять recall на размеченных задачах, сохранять доступ к исходной трассе в пределах retention.

### 3. Загрузка навыков и контекста

> Подтягивать только те инструкции, которые нужны текущему ходу.

Предлагаемая адаптация: По ходу пользователя и компактным описаниям разрешённого registry Jev может рекомендовать ID навыков. Существующий progressive loader остаётся исполнителем: только enabled версии, проверка ID и пересечение required tools с платформенным allowlist. Модель не пишет skills/policy и не добавляет права; оркестратор может выбрать иначе или уточнить задачу.

### 4. Типизированная компиляция вызова инструмента

> Каждый закрытый аргумент — отдельное решение; код допускает выполнение по самому слабому слоту.

Предлагаемая адаптация: Из закрытого списка функций и конечных вариантов аргументов формировать отдельные `choice`/`noul` вопросы. Код валидирует каждый слот по схеме и допускает только разрешённый вызов; слабый или неверный слот означает уточнение/отказ, а не best-effort выполнение. Порог по самому слабому слоту — предлагаемое правило допуска, не вычисленная совместная вероятность правильности.

### 5. Проверка цитат

> Код ловит выдуманные цитаты; Jev проверяет, подтверждает ли окружающий контекст утверждение.

Предлагаемая адаптация: Код сначала сверяет буквальную цитату, источник и диапазон текста; Jev советует `choice`: supported/unsupported/contradicted по утверждению и окружающему контексту. Хранить версию/ссылку источника; спорные случаи отправлять на проверку, а не превращать вероятность в доказанный факт. Пример ContentlY из Page — возможное применение, не готовая функция Builder.

### 6. Проверка извлечения

> Большинство записей заканчивается на дешёвом пути; к модели-«размышлятелю» попадают только сомнительные поля.

Предлагаемая адаптация: Детерминированный дешёвый extractor выдаёт поля и исходные spans; `noul`/`score` проверяют сомнительные соответствия. Только такие поля могут быть предложены для отдельного reasoning-прохода после проверки бюджета/согласия; уверенность не заменяет schema/type validation. Снижение цены и доля дешёвого пути требуют измерения, не обещаются.

### 7. Оценка трассы агента

> Превращает сырые траектории в метки для запросов, не прося другую модель писать рецензию.

Предлагаемая адаптация: По минимизированной трассе и профессиональной рубрике получать именованные метки progress/repetition/uncertainty через `choice`/`score`/`noul`, без свободной рецензии. Сопоставлять с фактическим исходом задачи и экспертными оценками, сохранять разногласия. Метка repeat 0.19 на схеме источника — иллюстрация, не порог и не измерение Builder; приложение к chaosbun пока предложение.

### 8. Семантические регрессионные тесты

> Стабильные числовые проверки пропускают изменения промпта, модели, инструментов и политик в CI.

Предлагаемая адаптация: Версионированный набор traces + рубрики может сравнивать изменения prompt/model/tools/policy по числовым ответам Jev. Это будущий eval, а не обещание детерминированности внешней модели. Обычный CI остаётся offline/deterministic; live eval — отдельно разрешённый, ограниченный бюджетом, с pinned model, допусками и экспертными labels. PASS не активирует policy автоматически.

### 9. Поиск кода Jevgrep

> Поиск по тому, что код делает, а не по точным словам.

Предлагаемая адаптация: В будущем локальный разрешённый индекс сначала находит ограниченные code snippets; Jev оценивает смысловую релевантность и ранжирует их ID. Jevgrep здесь название сценария из Page, не подтверждённый endpoint или установленный инструмент. Не выдавать доступ ко всей файловой системе, не отправлять секреты/закрытый код без прав и согласия; исходный код остаётся данными, не инструкциями.

### 10. Сопоставление сущностей

> Генерация кандидатов остаётся детерминированной; Jev решает вопрос смысловой идентичности.

Предлагаемая адаптация: Кандидаты Record A/B детерминированно отбираются локально; `choice` merge/review/no change — только совет о смысловой идентичности. Хранить исходные записи/ID, проверять схему и provenance; слияние или удаление требует отдельного разрешённого действия/проверки человеком. Дубли задач chaosbun — пример Page, не текущая интеграция и не автоматическое исправление доски.

### 11. Реранкер выдачи

> Эмбеддинги находят; Jev переупорядочивает по релевантности перед генерацией.

Предлагаемая адаптация: Реранжировать ограниченный набор passage/block ID через `score`/`choice` после первичного retrieval. Page описывает embeddings → Jev; текущий Builder использует локальный facet/lexical engine, embeddings не внедрены. Для блоков допускать только реально установленные blockId+variant+target, сохранять версию каталога; оркестратор может отвергнуть порядок или повторить поиск с уточнением.

### 12. Шлюз продвижения в память

> Продвигать только подтверждённые трассой переиспользуемые уроки; держать шлюз экспериментальным, пока тесты на recall его не подтвердят.

Предлагаемая адаптация: Из trace и evidence capture (Beacon — узел схемы Page, не установленная зависимость) предлагать `noul`/`score`/`choice` Promote/Discard для подтверждённых переиспользуемых уроков. Шлюз остаётся экспериментальным до проверки recall и вредных обобщений. Dataset не является памятью/инструкциями или обучением модели: отдельный анализ предлагает изменения, regression eval и человек активируют их. Никакой автоматической перезаписи memory/policy/skills.

## Порядок исследования и критерии допуска

Первый ограниченный кандидат: 11 (реранкер совместимого local shortlist) и 3 (совет по enabled skill registry).
Затем 5–8 на размеченных не-live fixtures; 2/12 требуют отдельной проверки сохранения фактов и recall.
1/4/9/10 зависят от отдельно спроектированных разрешённых adapters и не добавляют инструменты в текущий Builder.
Это приоритет исследования, не обещание даты или разрешение на интеграцию.

Для каждого сценария до реализации: замороженный набор профессионально размеченных кейсов, сохранённые
разногласия assessors, rubric/version, baseline без Jev, no-fit/ошибка/устаревшие ID/timeout/over-budget/privacy
кейсы, deterministic mock/replay и измерение фактических затрат только на отдельно разрешённой live-оценке.
Проверять false-positive/false-negative и полезность для результата, не только низкий разброс confidence.
Анализатор может предложить изменения, но human review/activation остаются обязательными по ADR-002.

Изменение t212 — только этот ADR и ссылки в документации. Нет runtime-кода, новых зависимостей, API/model
вызовов или затрат на Jev, сбора данных или изменений уже работающего поиска, skills, темы либо worker ресурсов.
